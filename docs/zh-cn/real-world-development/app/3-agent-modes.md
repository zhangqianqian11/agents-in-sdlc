我们先为项目添加了一项小功能，但更复杂的更改需要更完善的流程。GitHub Copilot app 可配合组织现有的工作流，帮助您用正确的方法构建所需功能。本系列课程将遵循典型的智能体驱动开发流程：从 issue 出发生成新功能，确认代码有效且功能行为符合预期，最终将更改成功合并到项目中。

> [!NOTE]
> 后续功能工作流会继续使用同一会话。通常，不同类型的文件会使用不同会话或 PR；这里会简化流程，以便聚焦核心概念。

本课将学习如何：

- 从 GitHub issue 启动新的智能体会话。
- 在 **Plan** 模式中确定需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续实现此功能时，您还将更新存储库指令、自定义现有 `quality-checks` 技能、添加 MCP 验证、创建 QA 智能体并创建功能 PR。

## 场景

Tailspin Toys 的游戏目录不断扩大，访问者需要按类别和发行商筛选游戏。待办 issue 已描述该功能，但在编码前还需要确定多个类别如何组合等细节。您将使用 Plan 模式解决这些问题，然后授权 Autopilot 执行范围明确的实现。

## 背景

将 AI 编码智能体引入开发流程不会改变基本原则。事实上，这些原则变得更加重要。大多数开发人员的流程大致如下：

1. 打开描述待办事项的 issue。
2. 为需要构建的内容制定计划。
3. 构建并审查代码。
4. 运行测试以验证代码。
5. 手动验证新功能。
6. 创建拉取请求 (PR)。
7. 代码通过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数流程都与上述步骤类似。

坚持这种标准流程，可确保 AI 生成的代码满足需求，并经历与手写代码相同的审查过程。

## 会话模式

**会话模式**控制智能体的自主程度。可以从提示框下方的下拉列表中设置模式，也可以随时更改：

- **Interactive**：您与智能体协作。智能体提出更改建议，并等待您输入后再继续。
- **Plan**：智能体先创建计划，您审查并批准后它才会执行。
- **Autopilot**：智能体完全自主工作，包括编写代码、运行测试和迭代，无需等待输入。

先在 Plan 模式中审查计划，再使用 Autopilot 实现。

## 从 issue 启动会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 已更新。

1. 在侧边栏 **Sessions** 下选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是已有的预置 issue，无需再创建一个。
2. 选择 **New session**，并选择基于更新后 `main` 的 **new working tree**。

    ![GitHub Copilot app 的 issue 视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认 issue 已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让智能体运行 `node --version` 和 `npm --version`。如果这些命令在终端中可用、但会话中不可用，请检查 app 的 PATH 或版本管理器设置，然后完全退出并重新打开 app。重试失败的操作和检查；不要仅因为智能体找不到 npm 就重新安装 npm。

## 规划筛选功能

规划让您可以在 Copilot 编写代码前审查实现方案。由于会话从 issue 启动，Copilot 已获得功能请求的上下文。发送：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并对照 issue 的验收标准审查计划。确认计划包含类别和发行商筛选、无障碍控件、数据访问更改和测试。讨论尚未明确的行为，例如多个类别如何组合，或没有游戏符合筛选条件时如何处理。

计划应使用项目现有工具运行 lint、单元测试、E2E 测试和类型检查。将计划范围限定为实现和测试筛选功能；完成质量工作流后再创建 PR。批准前要求调整不符合预期的部分，并记录 issue URL 和已商定的澄清内容，供后续验证使用。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中的等效选项。不要假定批准计划会自动切换模式；确认当前模式指示器显示 **Autopilot**。

Copilot 随后会按照计划开始实现功能、生成代码并运行测试。

> [!NOTE]
> 批准后可能会立即开始实现，因此请先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，请先解决设置问题，再认定检查已完成。只停止自己启动的服务器。

## 审查并验证实现

生成的代码与其他代码一样，必须在合并前审查。

1. 打开 **Changes**，检查筛选功能实现和测试。
2. 将结果与 issue 和批准的澄清内容进行比较，包括类别和发行商组合。确认更改遵循现有存储库指令。
3. 查看 lint、单元测试、E2E 测试和类型检查结果。跳过的检查不能算通过。
4. 接受实现前解决失败项，并重新运行受影响的检查。Playwright 的 E2E 配置会构建并提供预览服务，也可能复用本地服务器；确认测试所用服务器属于当前工作树，而不是上一课中的服务器。

## 体验新功能

代码看起来没有问题，但实际运行情况如何？像之前一样启动应用，并在浏览器画布中打开网站。

1. 使用以下提示让 Copilot 启动应用并在浏览器画布中打开页面：

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择一个类别，确认结果与类别匹配。清除筛选，再选择一个发行商，确认结果与该发行商匹配。
4. 组合类别和发行商筛选，并对照 issue 和已批准的计划检查结果。如果支持多个类别，还要验证约定的组合行为。
5. 测试没有游戏符合条件的组合，并检查空状态。清除或重置筛选，确认完整列表重新出现。
6. 完成后，使用以下提示让 Copilot 停止为此会话启动的开发服务器并关闭浏览器画布：

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 为后续课程保留此会话

暂时不要创建或合并筛选功能 PR。请保留此会话、工作树和分支，供第 4 至第 8 课继续使用。接下来会将自定义指令应用到筛选代码，然后添加技能和 QA 改进，最后在第 8 课中创建并合并 PR。停止开发服务器后，可让会话保持闲置，下一课再返回继续。

## 总结和后续步骤

您已使用不同的智能体模式构建并审查功能。本课中，您：

- 从 GitHub issue 启动了新的智能体会话。
- 在 **Plan** 模式中确定了需求。
- 使用 **Autopilot** 模式实现了新功能。
- 审查了代码。
- 在浏览器画布中手动验证了功能。
